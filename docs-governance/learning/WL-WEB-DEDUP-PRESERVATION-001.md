# WL-WEB-DEDUP-PRESERVATION-001

Status: IMPLEMENTED — PUBLIC ROUTE VERIFIED / CHAT VISUALIZER VERIFIED FOR ZERO-NETWORK SLICES

## Purpose
Prevent information loss, duplicate layering, review-surface failure, and stale or confusing factual presentation during incremental website recovery.

## Permanent rules

1. Resolve and freeze the authoritative baseline before editing.
2. Reuse exact baseline HTML/assets; do not structurally reconstruct a working page when exact source exists.
3. Inventory sections, assets, fragment links and protected blocks before subtraction.
4. Remove only evidenced redundant blocks.
5. Retained sections remain byte-identical unless explicitly authorized.
6. Protected sections require hard regression anchors: raw hash + image/link counts + relevant asset hashes.
7. Retained assets remain byte-identical.
8. Never claim no-information-loss without deterministic exact-source comparison.
9. Prefer the smallest subtraction or edit that resolves the stated problem.
10. Keep historical/rejected candidates recoverable.
11. After a user-visible contradiction, restart from the exact named baseline or latest explicitly approved candidate.
12. One requested delta per subversion; revise an unapproved proposal in place rather than inventing a new approved baseline.
13. Use a real browser when available before making visual claims.
14. Untouched external href values remain identical unless the current step is explicitly a link/source step; live reachability is a separate QA step.
15. Infographic deduplication preserves the designated graphic exactly and suppresses only the duplicate representation.
16. Review candidates must be static or zero-network for the in-chat review surface; do not rely on iframe, remote image/CSS/JS, fetch/XHR or redirect wrappers after a network-permission loop has been observed.
17. HTTP 200, deployment success or headless success never overrides a user-reported failure on the exact review surface.
18. Every candidate for Felipe review must have an in-chat HTML Preview when that surface supports it; a GitHub Pages route is supplemental context, not a substitute for the approval slice.
19. Do not advance to the next subversion or request content approval until the current delta is actually visible on the agreed review surface.
20. In-chat transport must preserve visible content/order/images/links for the represented slice; no screenshot-derived recreation or semantic approximation.
21. Workflow cadence: `baseline -> single delta -> deterministic preservation test -> browser when available -> zero-network delta Preview -> cumulative progress context -> user review -> next delta`.
22. A cumulative progress route is `REVIEW_TRANSPORT_ONLY`; it must never repoint the authoritative preview/release alias or imply promotion.
23. When the user asks for cumulative context, show the exact candidate from the top through the current frontier and hide downstream unreviewed sections only in transport.
24. Run an **intra-section redundancy scan** on every rewritten section. If a concept is already expressed by a primary block, do not repeat the same scope disclaimer or interpretation as multiple summary cards unless each repetition serves a distinct narrative function.
25. Use **one concept, one primary home** inside a section as well as across the site. Measurement geography, benefit geography, downstream continuity and phase decisions must be visually distinct rather than restated in several interchangeable cards.
26. Do not duplicate a confluence, junction or shared node in parallel process lanes when that layout can imply two different places or sequential events. Use one shared convergence node when the underlying system has one confluence.
27. Treat monetary values, project budgets, capacities, schedules and other volatile facts as time-sensitive. Do not present an old numeric estimate without date/context as though it were current; if public estimates have changed, either date the figure explicitly or keep the volatile chronology in the evidence register and use stable narrative language on the website.
28. When place names are used as monitoring or benefit anchors, distinguish `orientation anchor`, `candidate station`, `benefit geography` and `confirmed site`. Do not convert town spacing into scientific station design without hydrological justification.
29. Unsupported geographic superlatives such as `exact midpoint` must be removed or downgraded unless verified. A reasonable intermediate location is not automatically an exact midpoint.
30. Any future web-specific Skill must compose Incremental Control + Workflow Learning rather than duplicate them. Incremental Control owns one-delta gating; Workflow Learning owns failure classification; the web-specific layer owns HTML/assets/links/render/visualizer invariants.
